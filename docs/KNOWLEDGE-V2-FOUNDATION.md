# Универсальная RAG: контракт основы (этап 2)

Реализовано управление данными/правами/версиями. Действующие проверки остаются в nc5. Импорт старых СТО, карточек или уроков отсутствует. Нормативный исполнитель этапа 6 описан в [KNOWLEDGE-V2-REVIEW.md](KNOWLEDGE-V2-REVIEW.md); пользовательское переключение портала относится к этапу 8.

## Владельцы и хранение

Портал владеет учётными записями, областями доступа, членством, метаданными набора, запросами публикации и активным выпуском. Локальный `knowledge_v2.store.KnowledgeStore` владеет каноническими записями и manifest выпуска. Портальная `Release` — проекция, принимаемая по защищённому событию. Таблицы nc5 и `Batch`/`WorkerRun` не участвуют в выдаче v2-команд.

Канонические сущности хранятся в типизированной таблице `records(id, version, set_id, kind, payload, digest)`, а не в девяти копиях одинаковой схемы. Допустимые `kind`: `source_revision`, `fragment`, `requirement`, `obligation`, `dependency`, `applicability`, `review_proposal`, `review_case`, `clarification`. Для каждого вида проверяются обязательные поля; ссылки `[id, version]` выделяются в `record_links`. Существующая версия неизменяема, UUID записи не переезжает в другой набор, опубликованный manifest включает замыкание внутренних ссылок. Между наборами внешние нормативные ссылки пока сохраняются как неразрешённые зависимости; разрешение и проверка применимости относятся к этапу 4.

`source_revision` содержит SHA-256 и безопасный относительный ключ оригинала. Сохранение и чтение файла реализовано на этапе 3; см. [описание загрузки](KNOWLEDGE-V2-INGEST.md). `requirement` содержит модальность, условия и ссылки на точные фрагменты; семантическую корректность основы схемы нельзя выдавать за проверенную полноту выделения норм. Отдельные `generations`, `releases`, `release_state`, `snapshots`, `tasks`, `outbox`, `inbox`, `deliveries` реализуют жизненный цикл и возобновление. Schema version = 1 (протокол = 2). Создание схемы атомарно и идемпотентно; существующий чужой формат отвергается.

## Права

Области: personal / organization / team / project. Иерархия: organization → team → project, либо organization → project. Права члена родителя наследуются потомками. Personal не допускает общего членства. Создание корневой общей области доступно администратору, дочерней — управляющему родителем. Владелец области и активный администратор управляют её содержимым.

| Роль | Возможности |
|---|---|
| reader | Читать |
| contributor | Читать, загружать |
| reviewer | Читать, рецензировать |
| curator | Читать, загружать, рецензировать, публиковать |
| manager | То же и управлять членством |

Существующий `can_view_others` не даёт прав на знания. Создатель набора внутри команды не получает автоматически полномочий владельца команды. Удаление членства действует на следующий запрос; старый снимок не обходит актуальную проверку. Членство не редактируется через запросы worker. Изменения областей/членства/наборов/публикации записываются в `AuditEvent` в той же транзакции.

## HTTP API

Префикс `/normcontol/api/v2/`. Пользовательские маршруты требуют активной сессии и CSRF для POST. JSON-тело — объект до 2 MiB; неизвестные поля отвергаются. Рабочие маршруты требуют отдельного bearer token длиной от 32 символов (`NORMCONTROL_KNOWLEDGE_WORKER_TOKEN`), не используют токен старого bridge; worker ID задаётся доверенной конфигурацией.

| Метод и маршрут | Вход | Результат |
|---|---|---|
| GET `scopes/` | — | Только доступные области |
| POST `scopes/` | `name`, `kind`, необязательный `parent_id` | 201: `id`, `name`, `kind` |
| POST `scopes/{id}/memberships/` | `user_id`, `role`; null удаляет членство | 200; нужно manage |
| GET `normative-sets/` | — | `sets`, `empty`, `engine_generation=v2` |
| POST `normative-sets/` | `name`, `scope_id`; заголовок `Idempotency-Key` | 201: пустой набор, команда регистрации в outbox |
| GET `normative-sets/{id}/` | — | Метаданные и доступные выпуски |
| POST `normative-sets/{id}/publish/` | `release_id`, целое `expected_revision`; `Idempotency-Key` | 202: `command_id`, `state` |
| POST `snapshots/` | `job_id` UUID, `set_ids` | 201: неизменяемый снимок нормативных выпусков |
| GET `snapshots/{id}/` | — | Снимок владельцу/администратору после повторной проверки прав каждого набора |
| POST `worker/claim/` | `protocol_version=2`, `capabilities` | Одна команда с lease либо null |
| POST `worker/events/` | `event_id`, `command_id`, `lease`, `payload`, `payload_hash` | Подтверждение доставки |

Коды: 400 неверный контракт, 401 нет сессии, 403 нет прав/worker token, 404 неизвестный объект, 409 конфликт версии/idempotency/lease, 422 набор не готов, 503 временная ошибка БД. Внешний запрос не задаёт owner/actor/runtime signature.

Снимок HTTP API на данном этапе фиксирует нормативные выпуски и серверную метку `runtime_binding=pending-stage6`. Он не запускает обработку и не является утверждением о версиях реально применённых LLM/парсера. Полное связывание со штатным заданием и фактической моделью выполняется на этапе 6; браузер не может подставить эти версии.

API загрузки файлов реализовано на этапе 3; его маршруты и ограничения описаны в [KNOWLEDGE-V2-INGEST.md](KNOWLEDGE-V2-INGEST.md). API рецензий относится к этапу 7. Пустые ответы-заглушки не имитируют обучение.

## Команды, публикация, сбои

`set.register` переносит только новые метаданные набора. `source.ingest` передаёт новый оригинал и структурные фрагменты в отдельное хранилище; результат и журнал покрытия имеют собственные подтверждения. `release.prepare` — внутренний контракт будущего выделения требований и индексации: известные source revision IDs, версии преобразований, целевой release ID. Текущий bridge объявляет `set.register`/`source.ingest`/`release.publish` и не захватывает подготовку выпуска, которую пока не умеет выполнять.

После будущего индексирования trusted worker передаёт `release.ready`: manifest, SHA-256, подтверждения canonical/FTS/vector/provenance, пространство эмбеддингов, число записей и watermark. Портал сверяет это с исходной командой. Пользователь не может послать ready через сессию. Объекты записи и поколение существуют до ready; одних моделей БД недостаточно. На этапе 2 ready используется только в синтетических интеграционных тестах.

Publish проверяет права, ожидаемую metadata revision и готовность выпуска, создаёт команду атомарно. После подтверждения каноническим хранилищем портал переключает active pointer. Предыдущий manifest сохраняется для снимков. Новая публикация не меняет старый снимок. У одного набора одновременно не более одного запроса публикации.

Команды имеют три попытки по умолчанию, lease 120 с, защиту от старого владельца и durable receipt. Worker атомарно фиксирует изменение + inbox + outbox. Перед HTTP-доставкой сохраняется envelope. После потери ответа или перезапуска процесс повторяет тот же event ID; если портал успел принять событие, возвращается прежнее подтверждение. Если lease уже заменена, старый ответ отвергается; новая доставка переиспользует прежний канонический результат. Дубли с изменённым содержимым — конфликт.

Локальные processing tasks имеют курсор, ограниченные попытки и восстанавливаемую lease. При потере процесса истёкшая lease возвращает задачу в pending, а после исчерпания попыток — в failed. `checkpoint` проверяет lease; старый исполнитель не может подтвердить чужую задачу.

Немедленное распространение ACL в поисковые кеши/индексы добавляется при их появлении на этапе 5. Сейчас кешей прав нет: HTTP, claim и принятие результата каждый раз обращаются к текущим правам портала; каноническое чтение снимка требует переданный доверенным адаптером актуальный callback авторизации. Прямой сетевой API канонического хранилища не опубликован.

## Проверки и поставка

Команды запуска, Docker и откат: [deploy/knowledge-v2/README.md](../deploy/knowledge-v2/README.md).
