# Отбор нормативных требований для испытаний

Тестовый выпуск `screened_test` позволяет проверить реальный документ по полным,
обоснованным карточкам, не объявляя завершённым весь разбор нормативного источника.
Обычный выпуск `complete` по-прежнему запрещён при незакрытых вопросах полноты.

В составе выпуска различаются:

- **Рабочие требования**: обязательство или прямой запрет с проверенным происхождением,
  определённым профилем и применимостью, полным составом условий и исключений.
- **Кандидаты**: недостаточно раскрытая ссылка, неясные условия, неполная формулировка,
  спорная обязательность, смысловая неопределённость или вопрос полноты исходного пункта.
  Их сохраняют для эксперта, но не исполняют как требования при автоматической проверке.
- **Справочные записи**: определения, рекомендации, разрешения, допущения. Они не создают
  обязательных проверок. Определения доступны для поиска в глоссарии.
- **Точные повторы**: совпадают источник, профиль, смысловые поля, параметры и цитаты.
  Нечёткое сходство не является основанием для автоматического слияния.

Количество требований не ограничивается квотой. Уверенность модели ниже 0,9 направляет
карточку к эксперту; высокая уверенность сама по себе не делает карточку пригодной.
Отдельная контекстная проверка сопоставляет отобранные формулировки с полными исходными
пунктами, соседними условиями и структурными ссылками. Она может только понизить статус.
Текст внутри блока «Пример» не становится обязательным из-за слов «должен» или «запрещено»:
до следующего структурного заголовка такие карточки направляются эксперту. Это правило
работает и для длинных примеров, начало которых не попало в короткое окно соседних абзацев.

## Работа эксперта

Откройте «Нормативная база» → «Состав, доверие и изменения». Фильтр «Кандидаты» показывает
причину исключения и ссылку на двухпанельный редактор с исходной цитатой. Исправление,
обоснование и подтверждение сохраняются отдельной версией. Затем собирают новый выпуск.
Подтверждение одной карточки не закрывает вопрос полноты всего исходного пункта.

Публикация набора не равна утверждению каждой карточки. Рабочие требования, ещё не
подтверждённые экспертом в текущем контексте, дают только предварительные замечания.
Неприменимые профили не передаются модели для содержательной проверки.

## Подготовка на локальном исполнителе

Включите `KNOWLEDGE_QUALITY_SCREENING=1` для `knowledge-worker`: контекстный аудит выполняется
после смыслового анализа, последовательно с другими обращениями к GPU. Кэш и прогресс
хранятся в том же каноническом томе. VPS выполняет только интерфейс и команды управления.
В поставляемой конфигурации Docker Compose эта проверка включена по умолчанию.

Для уже завершённого анализа запустите в окружении локального исполнителя:

```text
python -m knowledge_v2.quality_audit <run_id>
```

`run_id` берётся из результата `source.analyze`. Используются уже настроенные переменные
`NORMCONTROL_KNOWLEDGE_DATA`, `NORMCONTROL_LLM_ENDPOINT`, `KNOWLEDGE_LLM_REVISION` и ключ LLM,
если он необходим. Контекст не обрезается: непоместившийся или невалидный ответ направляет
карточки в кандидаты. Прерывание сохраняет успешно обработанные порции.

После анализа без технических ошибок доступна сборка тестового набора. Выпуск закрепляет
исходники, анализы, карточки, экспертные версии, результаты контекстного аудита и полный
список оставшихся вопросов. Старые выпуски и проверки сохраняют свои снимки.

Отчёт раздельно показывает результаты по рабочему набору и ограничения нормативного
охвата. Даже 100% обработки выбранных требований не означает полного соответствия СТО.
