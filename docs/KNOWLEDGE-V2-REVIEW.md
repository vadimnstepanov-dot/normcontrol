# Нормативный конвейер v2 — этап 6

Отдельный исполнитель `knowledge_v2.review.ReviewRunner` проверяет документы по опубликованным выпускам новой нормативной базы. Он не импортирует старый каталог или уроки nc5. Действующие задания nc5 продолжают использовать прежний исполнитель; обновление не переключает их на v2.

## Путь проверки

1. Приём DOCX/DOC/PDF и однократное извлечение текста, структуры, таблиц, числовых фрагментов и непрочитанных областей. Исходные хеши проверяются до и после чтения. Полный извлечённый корпус сохраняется в задании.
2. Выбор одного или нескольких профилей **для каждого документа**. Профили и их предки берутся из закреплённого выпуска. Применимость требует фактов с проверенным происхождением. Неизвестная применимость остаётся неизвестной.
3. Полный реестр атомарных обязанностей из manifest, без ограничения top-k. Примеры и определения не являются обязанностями. Зависимости, условия, родительский контекст и таблицы загружаются с проверкой канонических хешей. Неразобранная норма не превращается автоматически в подтверждённое требование.
4. Неизменяемый снимок закрепляет выпуски, поколения, пространства эмбеддингов, профили, модель, параметры контекста, схему ответа, политику, факты и хеши документов.
5. Подтверждённые применимые обязанности группируются: один текстовый фрагмент передаётся один раз в группе. Подбор частей использует токенизатор самой LLM и двоичный поиск вместимости. По возможности сохраняются границы разделов. Контекст включает резерв на ответ и перепроверку; слишком большой атом не обрезается, а остаётся явно непроверенным.
6. Проверка выдаёт решение по каждой обязанности с точными цитатами. Определённые выводы затем независимо перепроверяются на том же тексте и паспорте полноты; `unknown` сохраняется вопросом без повторной генерации. Некорректный ответ повторяется не более одного раза.
7. Итог объединяет обязанности с учётом `all_of`/`any_of`. Допустимая альтернатива не считается нарушением из-за невыполнения другого варианта. Число нарушений считается по составным требованиям, отдельно от охвата атомарных обязанностей.

Отсутствие во всём документе подтверждается только при проверке всех запланированных частей, совпадении объединения переданных блоков с полным корпусом и отсутствии непрочитанных областей. Положительное решение также требует доказательств. Для нормы с областью `package` планируется весь переданный комплект. Источник может содержать неизвестные или внешние зависимости — они отражаются как ограничения, а не додумываются.

## Запуск

### Планирование v2.2

Сначала определяется подтверждённый тип и объём документов, затем применяется полный реестр требований выбранных профилей. Планировщик сравнивает размещение всего документа с группами требований и полный проход группами по частям. Выбирается вариант с меньшим числом задач, затем с меньшим повтором исходного текста. Это две эвристики, а не обещание математического глобального оптимума. До восьми обязанностей могут использовать один набор доказательств; зависимости и точные тексты норм сохраняются.

Транспорт `normative-wire-v3` передаёт одинаковые структуры и нормативные контексты через справочники. Длинные технические ID заменяются обратимыми короткими ID; таблицы, заголовки, условия, исключения и непрочитанные области сохраняются. Исходный корпус, происхождение и полный список блоков остаются в каноническом журнале. Вывод об отсутствии по выборке запрещён. Каждый бюджет измеряется токенизатором текущей модели с резервом ответа и перепроверки.

При переходе между версиями портал маршрутизирует новые задания по `planning_version=context-budget-v3` и признаку обработчика `features`. Старые исполнители не берут новые задания; новые не подхватывают старые закреплённые снимки. Перед заменой исполнителей требуется управляемая пауза старой проверки. Повтор создаёт новую версию пакета и сохраняет прежний отчёт.

`planning` и `performance` в отчёте содержат размер корпуса, применимость, число задач и фактические вызовы модели. Скорости генерации и prefill берутся из `timings` реальных ответов; стендовые генерации не запускаются. Небольшой атомарный файл `llm-telemetry.json` содержит только числовые показатели и время ответа. Монитор читает его раз в минуту. Linux-путь задаётся через `NORMCONTROL_KNOWLEDGE_DATA`, произвольный путь — через `NORMCONTROL_KNOWLEDGE_TELEMETRY`; для Windows/WSL имя дистрибутива задаётся `NORMCONTROL_KNOWLEDGE_DISTRO` (по умолчанию `NormControl`). Старый монитор nc5 не применяет свои решения об автоперезапуске к этим показателям: управление новой проверкой должно сохранять её собственные контрольные точки.

Это служебный интерфейс локального обработчика. Пользовательская интеграция нового режима в портал относится к этапу 8; рабочий портал пока не переключается.

Перед запуском задайте `NORMCONTROL_KNOWLEDGE_DATA`, `NORMCONTROL_KNOWLEDGE_PORTAL` (адрес `/normcontol/api/v2`), отдельный `NORMCONTROL_KNOWLEDGE_WORKER_TOKEN` и `NORMCONTROL_LLM_ENDPOINT`. Токен передаётся через окружение, не через файл спецификации или аргументы. Нужен фактический ID пользователя портала. Права проверяются заново через портал при планировании, запросах модели, выдаче отчёта и управлении заданием.

Пример **служебной** спецификации (идентификаторы выпусков и профилей заменяются реальными):

```json
{
  "paths": ["/input/project.docx"],
  "profiles": {
    "project.docx": {"RELEASE_ID": ["PROFILE_ID"]}
  },
  "document_types": {"project.docx": "Техническое задание"}
}
```

Тип документа подтверждается точным совпадением с текстом начала документа; если такого подтверждения нет, применимость не объявляется установленной. Общие профили используют закреплённый выбор нормативных источников. Другие проектные факты можно передать через программный интерфейс с доверенным проверяющим происхождение; текст документа сам не назначает себе права или статус нормативной применимости.

```bash
python -m knowledge_v2.review_worker --user-id 1 create --spec /input/review.json
python -m knowledge_v2.review_worker --user-id 1 run-once
python -m knowledge_v2.review_worker --user-id 1 pause TASK_ID
python -m knowledge_v2.review_worker --user-id 1 resume TASK_ID
python -m knowledge_v2.review_worker --user-id 1 report TASK_ID --output /output/report.html
```

На Windows задайте `PYTHONPATH` на каталог `sto_rag` и используйте Windows-пути. В Linux/WSL рекомендуется существующий Docker-образ `knowledge-worker`: он уже содержит парсеры DOC/DOCX/PDF и модуль `review_worker`. Пример одноразового запуска с входной папкой только для чтения:

```bash
docker compose --profile worker run --rm \
  -v /absolute/input:/input:ro \
  -e NORMCONTROL_LLM_ENDPOINT \
  knowledge-worker python -m knowledge_v2.review_worker --user-id 1 create --spec /input/review.json
docker compose --profile worker run --rm -e NORMCONTROL_LLM_ENDPOINT \
  knowledge-worker python -m knowledge_v2.review_worker --user-id 1 run-once
```

Адрес LLM должен быть доступен **из контейнера**. `127.0.0.1` внутри контейнера не является Windows-хостом. Нативный llama-server остаётся вне контейнера; Docker запускает обработку нормативов на локальном компьютере, а не на маломощном VPS. Для постоянной очереди вызывающая служба повторяет `run-once`; бессрочный демон и пользовательские кнопки не маскируются этим CLI.

## Остановка, восстановление и отчёт

Пауза действует на границе запроса: текущая проверка/перепроверка заканчивается и сохраняет результат. Завершённые части не повторяются. Явная команда `resume` после технической ошибки повторяет только части без сохранённого результата, сохраняя снимок и успешные решения. Незавершённый запрос после аварии допускает повтор; запись результата защищена арендой задания и курсором. Истёкшая аренда восстанавливается с ограниченным числом попыток. При изменении модели или закреплённых настроек возобновление блокируется. Приостановленное задание не блокирует следующее. Задания разных владельцев не смешиваются.

Просмотр отчёта и команда паузы доступны при выключенной LLM. Отзыв нормативного выпуска запрещает новое выполнение, но сохраняет доступную владельцу историю. Отзыв прав пользователя запрещает выдачу нормативных цитат даже из старого отчёта.

Отчёт JSON/HTML содержит снимок, охват, составные решения, нарушения, точные цитаты, расположение в документе, ограничения, ошибки частей, прогресс и приблизительное оставшееся время. `partial` означает наличие непроверенных обязанностей или ошибок. Охват **выделенных** обязанностей не доказывает полноту исходного нормативного корпуса.

## Границы приёмки

Проверены Windows и Linux-контейнер, отказ доступа, бюджет, неполный корпус, цитаты, составные требования, пауза и владельцы. На отдельной реальной Qwen 27B проверены синтетические положительный и отрицательный случаи. Это не статистическая оценка precision/recall на реальных СТО и не нагрузочный тест десятикратного корпуса — они остаются в программе последующей приёмки.

В этой версии для глобальных выводов используется полный текстовый проход. Он консервативнее поиска отдельных доказательств и может быть дороже на больших документах. Извлечение структурного корпуса выполняется один раз; неизвестные нормы и применимость не расходуют генерацию. Семантическая проверка схем и изображений этим модулем не реализована: такие области сохраняются как ограничения и блокируют глобальные утверждения.
