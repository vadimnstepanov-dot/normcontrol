# Проверка чистого релиза и измерения времени

Изменения подготовлены на базе тега `0.9.0`, коммит
`4598e4c3af0c365e84f7ad9ff6c8526714f0fb67`. Это первые два шага плана
аудита: воспроизводимый релиз и измерения (этапы 0–1 в подробной таблице).
Алгоритм выбора требований и правила принятия решений не изменены.

## Чистое окружение

Python 3.12. Создайте отдельное виртуальное окружение и установите зависимости:

```text
python -m venv .venv
# Активируйте .venv стандартным способом для вашей ОС.
python -m pip install -r requirements-test.txt -c requirements-test.lock
python -m pip check
python tools/test_release.py
```

`requirements-test.lock` фиксирует проверенные прямые и транзитивные версии.
Скрипт запускает тесты nc5, Knowledge v2 и обоих приложений портала.
Данные портала создаются во временном каталоге. Интеграционная проверка живой
LLM выключена; она требует явного `KNOWLEDGE_LIVE_SEMANTIC_TEST=1` при отдельном
запуске. В CI предусмотрены Windows и Linux. Запуск CI на GitHub происходит
после публикации ветки, локальная проверка сама его не запускает.

Исправлен импорт `document_units.units_for_document`. Публичные тесты
получили синтетический каталог из `nc5/tests/catalog_fixture.py` вместо
зависимости от частных нормативов. Приложение этот каталог не загружает.
Запрет нормативной проверки nc5 без настоящего каталога сохранён.
Тесты с искусственной моделью проверяют программные контракты, а не качество LLM.
Проверка контейнеров с LibreOffice, OCR, индексом и резервным копированием остаётся
отдельной: `deploy/knowledge-v2/test-install.sh` со своими внешними предпосылками.

## Замеры в рабочем движке

`knowledge_v2.performance` не имеет внешних зависимостей. Он включается на время
`nc5.Engine.run` и `knowledge_v2.check_runtime.execute`, независимо от подробного
журнала содержимого. Экспорт nc5 создаёт отдельную сессию того же задания.

Файл: `<data-directory>/performance/<SHA-256(job-id)>.jsonl`.
У nc5 каталог данных определяется расположением базы `Store.path`;
у Knowledge v2 — `store.directory`. Идентификатор хешируется для безопасного
имени файла. Возобновление добавляет новую сессию, а не затирает прошлые измерения.

```text
# PYTHONPATH должен включать sto_rag.
python -m knowledge_v2.performance <data-directory> --job <job-id>
# Либо непосредственно файл:
python -m knowledge_v2.performance <file.jsonl>
```

В отчёт nc5 добавлен `metrics.performance`. Завершённые измерения Knowledge v2
читаются из отдельного файла: контракт неизменяемого ответа порталу не менялся.
Итоговые файлы отчёта nc5 содержат снимок измерений перед записью экспорта;
длительность самого экспорта доступна после его завершения в JSONL.

Замеряются разбор, локальные правила, язык, оформление, реестр, планирование,
классификация, факты, шаблоны, трассировка и визуальный этап. Отдельно записываются:

- `http.template`, `http.tokenize`, `http.metadata`: служебные запросы;
- `queue.wait`: получение общего FIFO-слота Knowledge v2, включая таймаут;
- `queue.held`: время владения слотом, которое может включать планирование;
- `http.generation`: HTTP-вызовы генерации, включая возможное ожидание внутри сервера;
- `v2.check`, `v2.verify`, `nc5.stage.*`: логические стадии;
- числовые наблюдения о токенах, попаданиях в кеш, повторных попытках;
- `server.prompt_ms`, `server.predicted_ms`: серверные prefill/decode, если сервер их вернул;
- первый подтверждённый результат nc5 / первый готовый пакет и предварительное
  нарушение v2, отдельно для каждой сессии возобновления.

`seconds` включает вложенные стадии, `exclusive_seconds` исключает их.
Суммировать все `seconds` нельзя: это даст двойной счёт.
Prefill/decode уже входят в HTTP-время и не добавляются к нему.
`wall_seconds` суммирует завершённые сессии работы, не время паузы между ними.
Ожидание браузерной загрузки и очереди до захвата задания воркером сюда не входит.
Разность HTTP-времени и серверных таймингов нельзя автоматически объявлять очередью:
она включает сеть, сериализацию и другую работу сервера.

В JSONL отсутствуют тексты, ответы модели, имена документов, URL, ключи и сообщения
исключений. Имена стадий задаются кодом, значения наблюдений только числовые.
Сбой записи не отменяет результат проверки. Прерванная сессия или повреждённая
строка помечают сводку как неполную; при полностью недоступном хранилище метрики
могут отсутствовать. Файлы дописываются построчно; их хранение и очистку нужно
включить в эксплуатационную политику рядом с остальными диагностическими файлами.

## Воспроизводимый замер документа

```text
python tools/benchmark_document.py <document.docx> --output <new-output-directory>
```

Три прохода CPU сохраняют только числовые замеры и SHA-256. Первый включает
прогрев импортов и морфологии; следующие используют тот же процесс. Файл читается,
его контрольная сумма проверяется до и после. Это не заключение о соответствии.

Для сравнения с частным сохранённым заданием используйте локальный JSON
`{"payload": <tasks.payload>, "cursor": <tasks.cursor>}` только этой редакции:

```text
python tools/benchmark_document.py <document.docx> --output <new-output-directory> --baseline <private-snapshot.json> --endpoint <trusted-local-llama-endpoint> --plan
```

Команда проверяет SHA-256, агрегирует прошлые генерации, измеряет точный подсчёт
токенов и дважды перестраивает план с прежними нормативными строками и областями.
Проверяются идентификаторы всех полученных пакетов. Новая генерация не запускается.
Флаг `--plan` требует `--baseline` и `--endpoint`. Это может создавать тысячи
служебных запросов и должно запускаться как диагностический эксперимент.
Частный снимок и документ не должны попадать в публичный репозиторий.

Результат одного документа не даёт p95 по пользовательскому корпусу или оценку
полноты найденных ошибок. Для этого нужны несколько размеченных документов,
одинаковые нормативы и конфигурация модели. Полное чтение на CPU также не означает,
что смысловые требования можно автоматически закрыть формальными правилами.
