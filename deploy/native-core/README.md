# Основной обработчик в Docker/WSL

Развёрнуто 02.10.2026 в WSL `NormControl`. Специализированные правила `nc5` не изменены: адаптеры платформы находятся в `sto_rag/native_core`.

## Компоненты

| Компонент | Размещение | Память |
|---|---|---|
| Основной обработчик, планирование и подготовка | Docker `worker` | 2 ГиБ, 2 CPU |
| Общая очередь SQLite, зависимости, TLS-шлюз | Docker `gateway` | 384 МиБ |
| Локальный API/интерфейс | Docker `api` | 768 МиБ |
| RAG, нормативные обработчики, индекс | Существующие контейнеры WSL | Существующие лимиты |
| GPU-модель, аппаратная телеметрия, Microsoft Word | Windows | Существующая модель |

Канонические данные основного обработчика: `/opt/normcontrol/native-core/data` на Linux-диске. Контейнеры используют `/data/nc5`. Очередью `pipeline.sqlite3` управляет шлюз; остальные компоненты обращаются по API. SQLite не размещается на `/mnt/c` или SMB.

CPU-подготовка может выполняться одновременно с GPU-проверкой. Допускаются две CPU-задачи и одна GPU-задача, при наличии RAM. Резерв Windows — 2048 МиБ; дополнительный резерв WSL — 512 МиБ. Кэш документов ограничен 1024 МиБ и дополнительно уменьшается с учётом доступной памяти контейнера. Эти ограничения не увеличивают лимит WSL в 8 ГиБ.

## Мосты Windows

### DOC и DOCX

Образ основного обработчика: `normcontrol/native-core:0.9.5-wsl2-doc`.
DOC читается непосредственно Microsoft Word; текст и структура передаются общим
анализаторам как XML-части в памяти. Промежуточный файл DOCX не создаётся.
Контрольная сумма и идентификатор относятся к исходному DOC. Грамматика,
логика, RAG, нормативные правила, планировщик и очередь остаются общими.

Выгрузка сохраняет формат: DOC → DOC, DOCX → DOCX. Для DOC Word записывает
новый бинарный документ (формат 0), добавляет примечания с разделом «Основание»
и только проверенные структурированные редакции в режиме правок. Исходник,
прежние правки и примечания сохраняются. Неподтверждённые диапазоны, поля,
старые правки и другие потоки текста не заменяются по предположению; ограничения
отражаются в отчёте применения. Старые сохранённые планы DOCX продолжают
использовать закреплённую рабочую копию.

Чтение структуры не обходит все абзацы через COM. Диапазоны Word запрашиваются
только для выбранных замечаний, по 100 за запрос; кеш привязан к хешу исходника.
На ЧТЗ ЕСУД (4648 абзацев) проверено чтение за примерно 6 секунд вместе с запуском
Word, без изменения 410 примечаний и двух правок. Это замер подготовки, не
длительности всей проверки моделью.

DOC по-прежнему требует Windows-мост с установленным Word. Linux/Docker
выполняют общую проверку; замена Word на LibreOffice или Aspose не внедрялась.
Макросы и обновление внешних связей отключены. Защищённые документы требуют
действий владельца для внесения правок. На одну операцию Word установлен
тайм-аут 270 секунд; ошибки не выдаются за отсутствие нарушений.

Проверки: 30 тестов планов/доступа/экспорта локально и на VPS; реальный цикл
DOC → правки → повторное открытие в Word, TLS-шлюз, Linux-парсер и RAG.
Тестовые зависимости: `normcontrol-web/requirements-test.txt`.

`Start-Normcontrol.ps1` при наличии `sto_rag/data/nc5/wsl-core-active.json` запускает WSL-core и вспомогательные процессы, сохраняя текущую модель. Старый Windows-worker/gateway/API при этом не запускаются.

- `host_bridge`: TLS-передача счётчиков RAM, запросов модели и точный экспорт DOC/DOCX/PDF через Word. Word открывает источник только для чтения; макросы и обновление связей отключены. Проверяются контрольные суммы входа и выхода.
- `forwarder`: только пересылка байтов существующих портов 8098 и 8096 в WSL. TLS завершается в Linux-шлюзе. Сохраняется список разрешённых клиентов; адрес WSL определяется при запуске и обновляется.
- `windows_monitor`: аппаратные показатели Windows; очередь и актуальные скорости получает от Linux. Перед остановкой модели сохраняет контрольную точку, прекращает новые выдачи ресурсов и ждёт завершения всех GPU-билетов. Позднейшие пользовательские паузы не отменяются при автоматическом восстановлении.
- `sleep_guard`: предотвращает сон Windows, пока свежий heartbeat показывает активную проверку.

Чтение файлов через мост ограничивается точным списком `import_files`. В этой установке разрешены два явно предоставленных документа ЕСУД. Новые документы загружаются через закрытый портал. Произвольный доступ к папкам Windows не предоставляется.

Секреты не включаются в образ и Git. Они находятся в закрытых конфигурациях `C:/LM/normcontrol-v5/native-core` и `/opt/normcontrol/native-core/secrets`. Передаются уже настроенные токены/сертификат; проверка TLS не отключается.

## Сборка и запуск

Для текущей установки используется проверенный локальный базовый образ `normcontrol/review-worker:0.9.5-sto-lease-fix2`. Его идентификатор при сборке: `sha256:b9f932e5d88036d71980888e74a25fa725940b0262ce9fbca1652e1b288b0184`. На чистой машине сначала собирают базовый образ из `deploy/knowledge-v2/worker.Dockerfile`, затем указывают его через `CORE_BASE`.

```sh
docker build -f deploy/native-core/Dockerfile -t normcontrol/native-core:0.9.5-wsl1 .
cd /opt/normcontrol/native-core
docker compose up -d
docker compose ps
docker compose logs --tail 30
```

Лимиты, секреты и Linux-каталоги задаёт `compose.yaml`. Образы работают без root, с файловой системой только для чтения и отдельными writable-каталогами `/data/nc5` и `/tmp`. Автозапуск: `normcontrol-core.service` и Docker `restart: unless-stopped`. Windows-мосты запускаются через пользовательский автозапуск `NormControl Core` и штатный сценарий. Повторный запуск сценария не создаёт копии процессов.

## Плановые работы

Перед остановкой обработчиков включить страницу на портале, указав реалистичный срок. Команда выполняется на VPS с рабочим окружением Django:

```sh
python manage.py planned_maintenance on --minutes 15 --message 'Обновляем обработчик и очередь NormControl.'
python manage.py planned_maintenance status
```

Она возвращает пользователям страницу с HTTP 503, плановой длительностью, ожидаемым окончанием и автоматическим обновлением через 30 секунд. Рабочие API и статические файлы продолжают обслуживаться. Страница сохраняется при перечитывании приложения. Она не отключается автоматически по истечении срока: при задержке обновить оценку повторной командой `on`, после проверки сервиса выполнить:

```sh
python manage.py planned_maintenance off
```

На VPS установлен независимый маршрут Caddy из `maintenance.caddy`: **внутри** существующего `handle /normcontol/*`, перед `reverse_proxy`. Глобальный `route` после `handle` для этого не подходит. Django-настройка `MAINTENANCE_PUBLIC_DIR` указывает на `/var/lib/normcontrol-notice`; команда `on` атомарно создаёт там публичный HTML, а `off` удаляет его. Caddy отдаёт только эту страницу, без доступа к документам и без просмотра каталога. Обычное включение/выключение страницы не требует перезапуска или перечитывания прокси.

Поэтому страницу можно показать **до остановки** приложения и держать при остановленном Django/Gunicorn. Внешний веб-сервер Caddy при этих работах остаётся включённым. Проверено на публичном адресе: HTTP 503 с `X-NormControl-Maintenance: proxy`, сроком и `Retry-After: 30`; статика отвечает 200, worker-маршрут не перехватывается; после `off` портал отвечает 200. Приложение ради этой проверки не останавливалось. Первичная установка маршрута выполнена через проверку конфигурации и плавное перечитывание Caddy 2.11.4, без смены PID. См. [управление процессом Caddy](https://caddyserver.com/docs/command-line).

Обновление контейнеров выполнять после checkpoint-паузы через `/control/native/pause`, с дополнительным заголовком `X-Core-Control-Token`. Перед вмешательством в модель убедиться, что running GPU-билетов нет. Затем обновить контейнеры, проверить health, выполнить `/control/native/resume` с тем же токеном владения. Обычная пользовательская пауза имеет приоритет. Старые сценарии, напрямую перезапускающие `nc5.launch_worker` в Windows, после переноса не применяются.

## Сохранность и откат

Первичный снимок и журнал переноса: `outputs/wsl-core-migration-20261002`. Сохранены 11 проверок, 2611 задач, 1888 замечаний и 2105 ранее завершённых ответов модели; потерянных идентификаторов и изменённых ответов нет. Конкретные количества новых задач/замечаний растут в работающей проверке.

Для отката сначала показать страницу работ, сохранить checkpoint, дождаться текущего ответа, остановить только core-контейнеры и Windows-мосты. Сделать новую SQLite-backup и копию **актуальных** Linux-данных; восстановление старого снимка поверх новых результатов недопустимо. Сохранить текущую Windows-папку отдельно. Перенести актуальные Linux-данные в Windows, преобразовать `/data/nc5` в абсолютный Windows-путь, проверить хэши документов и базы. Снять маркер `wsl-core-active.json`, отключить Linux core и запустить штатный Windows-сценарий. Модель и ключи не меняются. Возобновлять только паузы, принадлежащие этому откату.

Полная перезагрузка компьютера/WSL во время пользовательской работы не выполнялась. Проверены пересоздание контейнеров с checkpoint, повторный запуск и перезапуск API при активном worker. Перенос сам по себе не меняет правила, скорость GPU-модели или ранее возникшие ошибки этапов проверки.


## Исправление восстановления после перезагрузки — 02.10.2026

Шлюз проверяет собственный TLS-маршрут `https://127.0.0.1:8098/core/health`, а не путь через Windows-forwarder. Проверка сертификата сохранена. В установленном образе `normcontrol/native-core:reboot-fix-20261002` изменён только healthcheck и добавлены его тесты; основной обработчик и API сохраняют прежний образ. systemd повторяет неуспешный запуск через 15 секунд.

Задание Windows `NormControl Core Recovery` запускает штатный сценарий при входе пользователя и повторяет его каждые две минуты для восстановления остановленных мостов и мониторинга. Пароль в задании не хранится; используется интерактивная сессия текущего пользователя. Сценарий защищён mutex от одновременных запусков; живые компоненты и модель повторно не запускаются. До входа пользователя в Windows работа Word-моста не гарантируется.

Проверено после фактического сбоя перезагрузки: три контейнера healthy, модель отвечает через TLS-шлюз, VPS видит модель и свежую телеметрию, страницы чата и создания проверки отвечают HTTP 200. Проверены повторные срабатывания задания с кодом 0. Новая полная перезагрузка компьютера ради теста не выполнялась.
