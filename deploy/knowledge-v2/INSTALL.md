# Установка и эксплуатация нормативной базы v2

Эта конфигурация создаёт **новую пустую** нормативную базу. Документы и рецензии прежней RAG не импортируются. Нормативная база — проверяемые источники, профили, версии требований и подтверждённый опыт рецензирования; изменение её записей не меняет веса LLM. Продукт соединяет рабочее пространство команды, заменяемую доверенную LLM и эту накапливаемую базу.

## Размещение

| Узел | Сервисы | Постоянные данные |
|---|---|---|
| Компьютер обработки: Windows + WSL2 или Linux | Qdrant, CPU-эмбеддинги, индексатор, обработчик; llama.cpp может работать нативно | `KNOWLEDGE_DATA_PATH`, том `qdrant-v2`, кэш модели |
| Сервер портала | Django-портал, HTTPS-прокси | том `portal-v2` или существующее серверное хранилище портала |

На текущем узле с ограниченной видеопамятью llama.cpp остаётся нативным: Compose не бронирует GPU и позволяет менять доверенную модель по её endpoint. На VPS с одним ядром не запускайте Qdrant, эмбеддинги и LLM. Профиль `portal` в этом Compose пригоден для отдельной установки/испытания; **он не переключает работающий портал на VPS**. Переключение рабочего портала выполняется только по согласованному плану. На текущей установке knowledge-v2 включён для ручной приёмки до этапа 10; независимая приёмка и нагрузочные испытания этапа 10 ещё не завершены.

## Вариант Windows / WSL2

1. В административном PowerShell на чистом Windows установите WSL: `wsl --install -d Ubuntu`, перезагрузите ПК, завершите создание Linux-пользователя. Убедитесь, что дистрибутив работает как WSL2: `wsl -l -v`. На уже подготовленном хосте повторная установка не нужна. Официальные указания: [Microsoft WSL](https://learn.microsoft.com/en-us/windows/wsl/install).
2. В Ubuntu внутри WSL2 установите Docker Engine и Compose plugin по [инструкции Docker для Ubuntu](https://docs.docker.com/engine/install/ubuntu/). Проверьте `docker version`, `docker compose version`. Пользователь, запускающий команды, должен иметь доступ к Docker; [группа docker даёт привилегии уровня root](https://docs.docker.com/engine/install/linux-postinstall/).
3. Храните `KNOWLEDGE_DATA_PATH` и кэш модели на Linux-файловой системе WSL2, например `/opt/normcontrol/data` и `/opt/normcontrol/models`. Не храните рабочую SQLite на `/mnt/c` или сетевом томе. Редактируйте и запускайте конфигурацию из WSL2: путь Windows `C:\...\RAG` доступен как `/mnt/c/.../RAG`.
4. Создайте каталог данных и кэш: `sudo install -d -o 65532 -g 65532 /opt/normcontrol/data` и `sudo install -d -o "$(id -u)" -g "$(id -g)" /opt/normcontrol/models`. Подготовьте кэш точной разрешённой ревизии E5: `bash deploy/knowledge-v2/preload-model.sh /opt/normcontrol/models`. Скрипт после загрузки проверяет, что UID 65532 читает веса и токенизатор; при повторной офлайн-проверке используйте `HF_HUB_OFFLINE=1`.

## Вариант Linux

На поддерживаемом 64-битном Linux установите Docker Engine и Compose plugin по [официальной инструкции для вашего дистрибутива](https://docs.docker.com/engine/install/). На Ubuntu последовательность установки пакетов приведена [здесь](https://docs.docker.com/engine/install/ubuntu/). Нужны Python 3.12 для `ops.py`, локальный диск с запасом под копии и загруженный через `preload-model.sh` кэш E5. Создайте каталог данных с владельцем UID 65532, как выше. Все дальнейшие команды выполняются одинаково на Linux и внутри WSL2.

## Первый запуск

В корне репозитория скопируйте `deploy/knowledge-v2/.env.example` в `deploy/knowledge-v2/.env`, заполните **абсолютные Linux-пути** `KNOWLEDGE_DATA_PATH`, `EMBEDDING_CACHE_PATH` и закреплённый `QDRANT_IMAGE`. Для изолированного портала задайте свой случайный `APP_SECRET` и `KNOWLEDGE_WORKER_TOKEN` длиной не меньше 32 символов. Для удалённого портала задайте `KNOWLEDGE_PORTAL_URL` с HTTPS и такой же токен на стороне портала. Секреты не размещайте в URL, Compose YAML или Git; установите `chmod 600 deploy/knowledge-v2/.env`.

```bash
docker compose -p knowledge-v2 -f deploy/knowledge-v2/compose.yaml --env-file deploy/knowledge-v2/.env config -q
docker compose -p knowledge-v2 -f deploy/knowledge-v2/compose.yaml --env-file deploy/knowledge-v2/.env up -d --build qdrant embeddings index-worker
docker compose -p knowledge-v2 -f deploy/knowledge-v2/compose.yaml --env-file deploy/knowledge-v2/.env ps
```

Проверьте локальные `/healthz` Qdrant и `/health` эмбеддингов; состояние всех трёх контейнеров должно стать `healthy`. Новая SQLite создаётся пустой, без набора СТО. Портал должен создать область и набор через UI; только после анализа, ручной оценки полноты и публикации выпуска можно запускать нормативный контроль. Первый запуск **не должен автоматически публиковать** источник.

Если портал развёртывается как изолированный Compose-профиль, сначала миграции, затем запуск:

```bash
docker compose -p knowledge-v2 -f deploy/knowledge-v2/compose.yaml --env-file deploy/knowledge-v2/.env --profile portal run --rm knowledge-portal python manage.py migrate --noinput
docker compose -p knowledge-v2 -f deploy/knowledge-v2/compose.yaml --env-file deploy/knowledge-v2/.env --profile portal up -d knowledge-portal
```

Изолированный профиль слушает loopback HTTP; для доступа снаружи необходим отдельный HTTPS-прокси. В образе `collectstatic` и WhiteNoise обслуживают CSS/JS. До подключения работающего портала проверьте права, миграции, выдачу CSS/JS и HTTPS. Профиль `worker` включайте только после проверки API и токена:

```bash
docker compose -p knowledge-v2 -f deploy/knowledge-v2/compose.yaml --env-file deploy/knowledge-v2/.env --profile worker up -d --build knowledge-worker
```

## Штатная пауза, обновление и откат

Сначала поставьте текущие проверки и выдачу новых заданий на паузу через интерфейс, дождитесь сохранения курсора и отсутствия `running`-аренд в канонической базе. Затем остановите обработчик и индексатор. Не прерывайте долгую операцию принудительно: сигнал завершения обработчик принимает между командами, а не внутри OCR/LLM-вызова. Если время штатного завершения превышает лимит, оставьте контейнер работающим и расследуйте причину. Команды ниже показывают общий порядок; перед остановкой проверьте состояние заданий.

```bash
docker compose -p knowledge-v2 -f deploy/knowledge-v2/compose.yaml --env-file deploy/knowledge-v2/.env --profile worker --profile portal stop -t 600 knowledge-worker index-worker knowledge-portal embeddings qdrant
python3 deploy/knowledge-v2/ops.py --project knowledge-v2 --env-file deploy/knowledge-v2/.env backup --data-dir /opt/normcontrol/data --target /secure-backups/knowledge-v2-YYYYMMDD
```

`ops.py` **откажется** копировать работающий контейнер или базу с активной арендой. Для копирования остановите также портал, эмбеддинги и Qdrant; процедура является холодной и согласованной для SQLite, файлов, Qdrant и портала. Копия содержит пользовательские документы и хеши паролей: храните её в закрытом каталоге, шифруйте при переносе. Снимок включает исходники, журнал покрытия, анализ, FTS, курсоры/снимки, Qdrant и том портала. `verify` сравнивает SHA-256 каждого файла и проверяет SQLite.

После копии обновите закреплённые образы и код, выполните миграции портала, поднимите сервисы. Пересоздание без удаления томов сохраняет данные. Проверяйте `healthy`, открытие опубликованного выпуска и точный поиск на контрольной цитате до возобновления очереди. Для отката верните предыдущее закреплённое дерево кода и образы; если схема данных несовместима, восстановите **в новую пустую установку** из копии соответствующей версии и переключите маршрут только после проверки. Не используйте `docker compose down -v`: флаг удаляет именованные тома [по документации Docker](https://docs.docker.com/reference/cli/docker/compose/down/).

## Восстановление

В новой пустой установке создайте **остановленные** контейнеры Qdrant и портала с новым Compose project name, не запуская их. Укажите пустой каталог данных. Затем:

```bash
python3 deploy/knowledge-v2/ops.py --project NEWPROJECT --env-file deploy/knowledge-v2/.env verify --source /secure-backups/knowledge-v2-YYYYMMDD
docker compose -p NEWPROJECT -f deploy/knowledge-v2/compose.yaml --env-file deploy/knowledge-v2/.env --profile portal create qdrant knowledge-portal
python3 deploy/knowledge-v2/ops.py --project NEWPROJECT --env-file deploy/knowledge-v2/.env restore --data-dir /new/empty/data --source /secure-backups/knowledge-v2-YYYYMMDD
```

В `.env` при восстановлении укажите `/new/empty/data`; существующие ненулевые каталог/тома блокируют команду. После восстановления запускайте Qdrant, эмбеддинги, индексатор и портал. Проверьте выпуск по manifest hash и точной цитате, затем состояние очереди/курсора. Токены и ключи из исходного `.env` в копию не входят: задайте их отдельно и согласованно на обоих узлах. Перед подключением текущих пользователей проверьте права доступа и отзыв ранее отозванных выпусков.

## Минутный мониторинг

```bash
python3 deploy/knowledge-v2/ops.py --project knowledge-v2 --env-file deploy/knowledge-v2/.env monitor --data-dir /opt/normcontrol/data >> /var/log/knowledge-v2-monitor.jsonl
```

Раз в 60 секунд пишется по одной строке JSON на контейнер (CPU, память, сеть), доступную GPU (нагрузка/VRAM) и состояние/этап задач (число, возраст старшей). Для `review.run` отдельно суммируется измеренное время завершённых пакетов из сохранённого курсора. Сборщик не обращается к LLM и не выполняет поиск; для разового замера есть `monitor --once`. Журнал ограничивайте средствами ОС, не помещайте на VPS данные локальных документов. Возраст ожидающей задачи сам по себе не является временем генерации. Измерения и формулу ETA сверяйте с реальными заданиями, а не с синтетическим курсором из smoke-теста.

## Приёмочный тест

`bash deploy/knowledge-v2/test-install.sh` создаёт два уникальных изолированных Compose-проекта и временные каталоги, проверяет пустой старт, здоровье, курсор после пересоздания, копию, хеши и восстановление. Скрипт выводит путь к закрытым временным данным; проверив результат, остановите **только эти именованные тестовые проекты** и удалите их тома. Не запускайте этот скрипт с производственным project name. Испытание проверено в WSL2/Ubuntu; отдельный физический Linux-хост ещё не испытан.


## Обработчики эксперта и трассировки (9.1.6–9.1.7)

Для новых проверок нужны актуальный `knowledge-worker`, отдельный `expert-worker` и `review-worker`. Последний принимает проверки комплектов и предложения нормативных связей, поэтому большой анализ источника не блокирует всю очередь. Все обработчики используют один и тот же **локальный** `KNOWLEDGE_DATA_PATH`. Модельные обращения сериализуются в общей FIFO-очереди; создание дополнительного обработчика не означает параллельного занятия одной GPU.

На Windows команды выполняются **в WSL2**, на Linux — в оболочке Docker-хоста. Нативная Windows-LLM доступна контейнерам через явно заданный доверенный адрес/шлюз; контейнерный `127.0.0.1` не является компьютером Windows. Не открывайте Qdrant наружу и не переносите SQLite между VPS и хостом.

```bash
docker compose -p knowledge-v2 --env-file deploy/knowledge-v2/.env \
  -f deploy/knowledge-v2/compose.yaml \
  -f deploy/knowledge-v2/compose.expert.yaml \
  -f deploy/knowledge-v2/compose.review.yaml \
  --profile worker config -q

docker compose -p knowledge-v2 --env-file deploy/knowledge-v2/.env \
  -f deploy/knowledge-v2/compose.yaml \
  -f deploy/knowledge-v2/compose.expert.yaml \
  -f deploy/knowledge-v2/compose.review.yaml \
  --profile worker up -d --build knowledge-worker expert-worker review-worker
```

Для обычного доверенного HTTPS-сервера используется стандартное хранилище CA образа. Для локального HTTPS-шлюза с собственной CA дополнительно загрузите `compose.local-llm.yaml` **и** `compose.review.local-llm.yaml`, задав `KNOWLEDGE_GATEWAY_CERT_PATH` — абсолютный Linux-путь к заранее проверенному сертификату. Эти файлы добавляют `SSL_CERT_FILE` и read-only mount сертификата обоим модельным обработчикам. Не отключайте проверку TLS. Для разрешённого локального HTTP endpoint сертификатные overlay не нужны.

Портал должен применить миграцию `knowledge.0010_normativelink` (создание таблиц связей и истории). Каноническая схема остаётся **1**, формат generation/embedding-space не меняется. Контракт новых проверок — `package-trace-9.1.6`; старые снимки продолжают жить с прежними версиями. Старый worker без возможности `trace.suggest` не получит новое поручение с трассировкой. Перед включением очереди проверьте версии worker и портала вместе, открытие редактора и матрицы, выдачу CSS/JS и экспорт Word/Excel.

При остановке/резервировании добавляйте **expert-worker и review-worker** к списку остановленных сервисов и используйте те же Compose-файлы, с которыми они были запущены. `ops.py` проверяет все работающие контейнеры выбранного проекта по Docker labels, включая дополнительные сервисы и старые контейнеры; работающий процесс не обходится неполным Compose-файлом. Каталог данных включает новые `review-batch-checkpoints`: успешные подгруппы после обрыва вывода не должны теряться из копии.

Обновление 0010 добавляет таблицы, не переносит старую RAG и не удаляет документы/курсоры. Сохраняйте предыдущие образы и код. Для отката сначала поставьте проверки на паузу, дождитесь сохранения и завершения активных вызовов, верните предыдущие образы/код; дополнительные таблицы можно оставить. Старый исполнитель не продолжает новый контракт автоматически. Полное восстановление БД выполняется только в отдельную остановленную пустую установку, по процедуре выше.

Реальная проверка этапа 9.1.7 выполнена на Windows, Docker/Ubuntu в WSL2 и портале Ubuntu/VPS. Изолированный старт, копия и восстановление проверяются `test-install.sh`. Это не испытание всего вычислительного стека на отдельном физическом Linux-хосте.

Эксплуатация связей и ограничения: [нормативная трассировка](../../docs/KNOWLEDGE-V2-TRACEABILITY.md). Этап 10 использует отдельный отложенный набор; контрольные примеры 9.1.7 его не заменяют.

### Доставка готового анализа

Включайте каталог `analysis-deliveries` в резервную копию всего канонического тома. Обработчик сохраняет готовый анализ до отправки карточек, вместе с хешем результата и состава команды. При сетевом отказе он отправляет те же порции, без нового смыслового анализа; статус `partial` и вопросы полноты сохраняются. Успешные порции принимаются идемпотентно. Получение нового задания не повторяется автоматически при неопределённом ответе, чтобы не захватить вторую команду.

Обычный worker создаёт эти файлы от собственного UID. При ручном восстановлении сохраняйте закрытые права и владельца тома: файл root с правами 0600 будет недоступен непривилегированному контейнеру. Не исправляйте это открытием данных всем пользователям. Восстановленные результаты сверяются с каноническими записями и идентификатором той же команды; нельзя подменять файл другим анализом или обнулять историю попыток.

Продление длительного анализа переживает временные сетевые ошибки в пределах срока аренды задания. Отзыв разрешения, устаревшая аренда и ошибка доверия сертификату не обходятся повторными попытками. Перед обновлением source-worker дождитесь сохранения активного ответа и штатного завершения процесса. Перезапуск только обработчика не требует перезапуска LLM.
